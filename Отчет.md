Получить практический опыт разработки безопасного backend-приложения и автоматизированной проверки кода на уязвимости. ## Ход работы

### Стек и проект

Приложение написано на Java 25 и Spring Boot 4.1. Сборка выполняется Maven. Данные хранятся в памяти в H2 через Spring Data JPA и Hibernate. Для защиты используются Spring Security, OWASP Java Encoder, SpotBugs с FindSecBugs и OWASP Dependency-Check.

### Реализованное API

Сервис запускается на `http://localhost:8080`. Ответы приходят в JSON. При старте создаются две учетные записи: `student` / `Student#Lab1` и `admin` / `Admin#Lab1`.

**POST /auth/login.** Принимает логин и пароль. При успехе возвращает JWT со сроком жизни 1 час. При ошибке возвращает 401 и одно сообщение «Неверные учетные данные», без уточнения, что именно указано неверно.

**GET /api/data.** Возвращает список объявлений. Без заголовка `Authorization: Bearer <token>` сервер отвечает 401. Параметр `q` ищет подстроку в заголовке и тексте объявления.

**POST /api/notes и GET /api/notes.** Собственный метод: личные заметки. Заметку можно создать только с действующим токеном. Список возвращает записи автора этого токена. Имя автора берется из JWT, поэтому подставить чужое имя в запрос нельзя.

### Защита от SQL-инъекций

Запросы к базе не собираются склейкой строк. Поиск объявлений записан на JPQL, а текст пользователя передается параметром `:query`. Hibernate отправляет его в prepared statement отдельно от текста запроса. Введенная строка `' OR '1'='1` остается условием поиска и не меняет логику выборки: в ответ приходит пустой список. Обычный поиск по слову «парол» находит одно объявление.

### Защита от XSS

Поля, которые пришли от пользователя и возвращаются клиенту, пропускаются через OWASP Java Encoder, метод `Encode.forHtml`. Символы `<` и `>` заменяются HTML-сущностями. Заголовок `<script>alert(1)</script>` в ответе выглядит как `&lt;script&gt;alert(1)&lt;/script&gt;`. Если клиент вставит такую строку в HTML, браузер покажет ее как текст. Длина полей ограничена проверкой на сервере. В ответах также выставляются заголовки `X-Content-Type-Options: nosniff` и `Content-Security-Policy`.

### Аутентификация

Пароль не хранится в открытом виде. При создании учетной записи он преобразуется алгоритмом bcrypt, в базе остается только хэш. API хэш не возвращает.

После успешного входа сервер выпускает JWT с алгоритмом HS256. В токене указаны логин, время выпуска, срок действия и роль. Подпись считается секретом сервера.

На защищенных методах стоит фильтр `JwtAuthenticationFilter`. Он читает заголовок `Authorization`, проверяет подпись и срок токена и только после этого пропускает запрос. Неверная подпись, пустой или просроченный токен дают ответ 401. Сессия на сервере не создается.

CSRF для этого API отключен: браузер сам не прикладывает заголовок `Authorization`, в отличие от cookie. Обычная CSRF-атака на сессию в cookie здесь не срабатывает.

### CI/CD

В репозитории добавлен файл `.github/workflows/ci.yml`. Он запускается при push и при создании pull request.

Статический анализ (SAST) выполняет SpotBugs вместе с FindSecBugs на фазе `verify`. Порог замечаний — Medium. Локальный запуск завершился без замечаний, отчет формируется в `target/reports/spotbugs.html`.

Анализ зависимостей (SCA) выполняет OWASP Dependency-Check. База CVE загружается из готового кэша OWASP, поэтому отдельный ключ NVD не требуется. Сборка останавливается, если найдена уязвимость с оценкой CVSS от 9.

В ходе работы разработано REST API на Spring Boot. Вход выдает JWT, закрытые методы без токена недоступны, пароли хранятся в виде bcrypt-хэша. SQL-запросы параметризованы, пользовательский текст в ответах экранируется. В CI подключены SpotBugs с FindSecBugs и OWASP Dependency-Check. Проверка в Postman подтвердила отказ в доступе без токена, безопасную обработку строки SQL-инъекции и экранирование HTML в заметке.

## Ответы на контрольные вопросы

**1. Почему хэширование пароля bcrypt предпочтительнее SHA-256?**

SHA-256 считается очень быстро, поэтому видеокарта может перебирать огромное число вариантов. Без отдельной соли для каждого пароля помогает и радужная таблица. bcrypt специально работает медленно, сам сохраняет соль и имеет настраиваемую стоимость вычисления. Когда компьютеры становятся быстрее, стоимость можно увеличить, а уже сохраненные хэши остаются проверяемыми.

**2. В чем основная разница между SAST и DAST?**

SAST анализирует исходный код или байткод и не запускает приложение. В этой работе так работают SpotBugs и FindSecBugs. DAST проверяет уже запущенное приложение снаружи: отправляет запросы и смотрит на ответы, как это делает OWASP ZAP. SAST раньше находит ошибки в коде, DAST показывает поведение и настройки работающего сервиса. Эти подходы дополняют друг друга.

**3. Как работает JWT и как сервер проверяет его подлинность?**

Токен состоит из трех частей: заголовка, полезной нагрузки и подписи. В заголовке указан алгоритм HS256. В нагрузке находятся логин, время выпуска, срок действия и роль. Подпись — это HMAC от первых двух частей, посчитанный на секрете сервера. Сервер заново считает подпись своим секретом, сравнивает ее с присланной и проверяет срок. Если подпись совпала и срок не истек, токен принимается. Хранить сессию на сервере для этого не нужно. Нагрузка токена не зашифрована, поэтому пароль в нее помещать нельзя.

**4. Какие риски возникают, если не проверять сторонние библиотеки?**

В приложение попадает чужой код, в том числе транзитивные зависимости, которые не выбирались напрямую. Известная ошибка в такой библиотеке может быть использована, даже если собственный код написан аккуратно. Пример такого класса проблем — Log4Shell. Проверка состава зависимостей сопоставляет версии библиотек с базой известных CVE до выпуска приложения.
